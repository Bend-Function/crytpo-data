# Crypto Market Data Collector 中文使用指南

## 1. 先了解当前可用范围

这个项目的目标是从 Binance、Bybit、Bitget、Kraken 和 OKX 的公开 REST/WebSocket API 采集价格、成交、ticker、盘口和衍生品指标，以交易所原始 payload 为核心写入本地文件。设计边界是只读、匿名、不下单，不访问账户、仓位、钱包或私有频道。

但是，当前代码尚未提供可靠的端到端长期采集命令。首先用下面的命令核对实际 CLI：

```bash
.venv/bin/collector --help
```

当前对用户稳定可用的入口只有：

```bash
.venv/bin/collector config check config.yaml
.venv/bin/collector config check config.yaml --json
```

| 能力 | 当前状态 | 边界 |
| --- | --- | --- |
| 严格分层配置、capability 检查、secret 引用校验 | 可用 | `config check` 不访问交易所，也不创建 data/state 目录 |
| Raw envelope、zstd 分帧写入、manifest、恢复和有界队列组件 | 代码和离线测试已有 | 尚未通过面向用户的长期采集 CLI 串起 |
| Direct/SOCKS 客户端、出口分配、限频/重试/调度和选币组件 | 代码和离线测试已有 | 配置可校验，但尚无 `run` 入口启动完整采集 |
| 五家交易所长期采集 | 尚未接入 | 当前 live smoke 只是直接检查公开 API |
| 30 秒及更大时间维度的 Parquet 汇总 | 尚未实现 | 配置模型已经会校验 `materializer` 字段，但不会产生汇总文件 |
| Aliyun OSS、S3、外部挂载 WebDAV 备份 | 尚未实现 | 配置模型和角色依赖已有，但没有上传、验证或 restore 命令 |

因此，现阶段不要尝试 `collector run`、`collector materialize` 或 `collector archive`；它们是计划中的入口，不是当前 CLI。

## 2. 环境与安装

### 2.1 前置条件

- Python 3.11 或更高版本。
- macOS 或 Linux；实际长期运行更适合独立 VM/容器和独立数据卷。
- 安装依赖和执行 live smoke 时需要网络。
- 公开市场 API 不需要交易所 API key。

### 2.2 本地开发/测试环境

在仓库根目录执行：

```bash
python3.11 -m venv .venv
.venv/bin/python -m pip install --require-hashes -r requirements/dev.lock
.venv/bin/python -m pip install --no-build-isolation --no-deps .
.venv/bin/collector --help
```

`dev.lock` 包含所有角色依赖和 pytest、Hypothesis、Ruff、mypy 等开发工具。安装项目代码后，如果源码发生变更，需要重新执行最后一条安装命令。当前可重现流程以普通 wheel/非 editable 安装为准，不要把 `pip install -e .` 当作生产安装方式。

### 2.3 按进程角色安装

| 角色 | 锁文件 | 额外核心依赖 | 当前进程入口 |
| --- | --- | --- | --- |
| collector | `requirements/collector.lock` | HTTPX SOCKS、python-socks、websockets | 只有配置 CLI；worker 组件可导入 |
| materializer | `requirements/materializer.lock` | PyArrow | 尚无 service/CLI |
| archiver | `requirements/archiver.lock` | boto3、oss2 | 尚无 service/CLI |
| development | `requirements/dev.lock` | 上述全部及测试/质量工具 | 可运行完整测试 |

每个锁文件都使用 hash 校验，应保留 `--require-hashes`。

仅安装 collector 角色时，使用：

```bash
python3.11 -m venv .venv
.venv/bin/python -m pip install --require-hashes -r requirements/build.lock
.venv/bin/python -m pip install --require-hashes -r requirements/collector.lock
.venv/bin/python -m pip install --no-build-isolation --no-deps .
```

`build.lock` 提供本地 wheel 构建工具，`collector.lock` 提供采集进程依赖；最后一条命令只安装当前项目，不再解析或下载依赖。

可用项目自带脚本在临时虚拟环境中验证角色隔离：

```bash
.venv/bin/python scripts/verify_role_locks.py --require-entry collector
```

该命令会创建临时 venv、下载锁定依赖并构建 wheel，所以耗时会明显高于普通单元测试。当前不要使用 `--require-entry materializer` 或 `--require-entry archiver`，因为对应服务模块尚未实现。

## 3. 配置检查

### 3.1 基本用法

```bash
.venv/bin/collector config check config.yaml
.venv/bin/collector config check config.yaml --json
```

也可以传入包含 `config.yaml` 的目录：

```bash
.venv/bin/collector config check .
```

成功时退出码为 0；配置/YAML/capability/secret 错误时退出码为 2。检查会：

- 解析严格 YAML，拒绝重复 key、anchor/alias、merge key、多文档和未知字段。
- 校验时长、容量、队列、磁盘阈值和交易所最大深度等静态约束。
- 解析所有 `env:`/`file:` secret 引用，但报告只输出引用，不输出明文。
- 输出配置 SHA-256 和 capability registry SHA-256。
- 不联网探测交易所，不创建 `data_root` 或 `state_root`。

`dynamic selection: unresolved`、`catalog_unresolved` 和 `live capacity: unresolved` 在当前是预期警告：`config check` 只做静态校验，尚未实现的 live probe 才能解析实际目录、Top-N、新币和实际限频容量。

### 3.2 配置文件与覆盖顺序

仓库中被 loader 自动读取的树形结构是：

```text
config.yaml
config/
  network.yaml
  profiles/<profile>.yaml
  exchanges/<exchange>.yaml
```

从低到高的覆盖优先级为：

```text
内置默认 < config.yaml < 选中的 profile < 对应 exchange 文件
```

对单个采集范围计算有效值时，继续按以下层级覆盖：

```text
全局 selection/books < exchange < market < symbol
```

字典会递归合并，但列表会整体替换，不会追加。例如 profile 中的 `quote_assets: [USD, USDT]` 会替换下层的 `[USDT]`。

如果 `config/network.yaml` 存在，它独占根配置的 `network` 子树，此时不能再在 `config.yaml` 中写 `network:`。选中的 profile 仍可以显式覆盖 network。`config/examples/*.yaml` 只是参考片段，loader 不会自动合并它们。

相对路径以根 `config.yaml` 所在目录为基准解析。时长必须显式带 `ms`/`s`/`m`/`h`/`d` 单位，容量必须带 `B`/`KiB`/`MiB`/`GiB` 单位。

## 4. 固定交易对、Top-N 和新币

默认计价资产是 USDT。根选择配置可写为：

```yaml
selection:
  quote_assets: [USDT]
  fixed_pairs: [BTC/USDT, ETH/USDT]
  top_n: 20
  refresh_interval: 5m
  turnover_max_age: 15m
  exit_grace: 30m
  capacity_policy: degrade_low_priority_with_warning
  new_listings:
    enabled: true
    capture_duration: 72h
    initial_lookback: 72h
```

设计中的最终选择集是以下三者的并集：

1. `fixed_pairs`：固定保留，优先级最高，不受 `quote_assets` 过滤。
2. `top_n`：对每个 `quote_assets` 分别按有效的 24h 计价成交额排名；离开 Top-N 后可继续保留 `exit_grace`。
3. `new_listings`：对符合计价资产过滤的新上市品种采集 `capture_duration`；`initial_lookback` 用于初始目录时间范围。

`top_n: 0` 可禁用 Top-N，`new_listings.enabled: false` 可禁用新币选择。`capture_duration` 必须大于 0，可在全局、exchange 或 market 层覆盖。

固定请求既可以写 canonical pair（如 `BTC/USDT`），也可以写交易所目录中的精确 instrument key（如 `BTC-USDT-SWAP`）。实际解析时优先精确 instrument key；canonical pair 必须在当前 `exchange/market` 中唯一匹配一个可交易品种，零个或多个候选都应失败。当前 `config check` 没有访问交易所目录，所以只会报告 `catalog_unresolved`，不会启动采集。

可在 `config/exchanges/okx.yaml` 中做更细覆盖：

```yaml
enabled: true
selection:
  fixed_pairs: [BTC/USDT]
markets:
  spot:
    enabled: true
    selection:
      quote_assets: [USDT]
      top_n: 10
      new_listings:
        capture_duration: 24h
    symbols:
      BTC-USDT:
        books:
          deep_snapshot:
            requested_interval: 1m
            depth: 1000
```

`symbols` 项只覆盖已被选中品种的行为，它本身不会把品种加入选择集。要强制采集，仍应在 exchange 或 market 层写入 `fixed_pairs`；`fixed_pairs` 不允许配置在 symbol 层。

## 5. WebSocket Live 与 REST 深度快照

```yaml
books:
  live:
    enabled: true
  deep_snapshot:
    enabled: true
    requested_interval: 30s
    depth: max_supported
    overload_policy: stretch_with_warning
```

这是两种独立产品：

- `book_live` 是高频 WebSocket snapshot/delta 原始流，深度和更新频率受交易所频道限制。
- `book_deep_snapshot` 是独立调度的 REST 离散深簿快照，可使用不同健康出口。

两者不桥接：REST 深度快照不会修补 live gap、不会扩大 live 深度，也不会生成第三种隐式 reconstructed book。后处理如果需要对比，应显式对齐两个数据集。

`depth` 可写正整数或 `max_supported`。`config check` 会拒绝超过已知 capability 上限的整数深度。在计划中的实际 scheduler 中，当 30 秒的 REST 请求超出当前限频容量时，`stretch_with_warning` 会拉长 effective interval 并记录警告；`fail` 则应在启动/重载前失败。当前只完成静态配置与调度组件，没有 CLI 会实际发出这些定时请求。

## 6. SOCKS 分流、限频与重试

参考配置位于 `config/examples/network-with-socks.yaml`。要使用它，将所需内容合并或替换到 `config/network.yaml`；仅修改 example 文件不会生效。

```yaml
egress_pool:
  - id: direct-primary
    type: direct
    quota_group: direct-primary
    max_http_concurrency: 8
    max_ws_connections: 20

  - id: socks-primary
    type: socks5h
    quota_group: proxy-nat-primary
    url: env:SOCKS_PRIMARY_URL
    max_http_concurrency: 4
    max_ws_connections: 10

assignment:
  strategy: rendezvous_hash

retry:
  rest_max_attempts: 5
  base_backoff: 250ms
  max_backoff: 30s
  ws_reconnect_max_backoff: 60s

scheduler:
  deep_snapshot_max_interval: 15m
  recovery_step_ratio: 0.20
  healthy_refreshes_before_step_down: 3
```

需要在运行 `config check` 之前通过安全的运行环境设置 `SOCKS_PRIMARY_URL`，或把引用改为 `file:/absolute/path`。配置中不能直接写带用户名/密码的明文 URL。

- `socks5h` 表示由代理端解析 DNS；`socks5` 使用本地 DNS。`type` 必须与 secret 解析后的 URL scheme 完全一致。
- `direct` 禁止配置 URL，并且网络客户端显式不信任 `HTTP_PROXY`/`HTTPS_PROXY` 等环境代理。
- rendezvous hash 为 WebSocket generation 提供稳定的初始出口归属；连接失效后新 generation 才可以改用其他健康出口。
- `quota_group` 是交易所限频/ban 预算的边界。如果多个代理共享同一公网 NAT/IP，必须使用同一 `quota_group`；多写几个逻辑代理不代表获得了独立限频配额。
- 重试组件使用有上限的指数退避与 full jitter，支持 `Retry-After`、429 throttle、418/显式 ban、5xx 和传输错误分类；不应通过立即切 IP 重放请求来绕过 ban。
- REST 深度快照与 live WebSocket 不绑定；它可以由 scheduler 选择任一健康 REST 出口。

上述客户端、状态库、调度和重试组件已有离线测试，但尚未由长期采集 CLI 统一启动。同时，`tests/smoke` 直接访问公开 API，不读取 `config/network.yaml`，因此不能用它验证配置的 SOCKS 分流。

## 7. Raw 数据目录与文件

实现采用“交易所 / 市场 / 品种 / 数据流 / UTC 小时”的布局，比单纯的 `./okx/btc` 多两层语义，用来区分 Spot/永续、live/deep 以及同一品种的多种数据流：

```text
<data_root>/raw/<exchange>/<market>/<instrument_key_encoded>/<stream>/<YYYY>/<MM>/<DD>/<HH>/
  part-<part_start_ns>-<sequence>.jsonl.zst
  part-<part_start_ns>-<sequence>.manifest.json

<data_root>/raw/<exchange>/_control/<YYYY>/<MM>/<DD>/<HH>/...
<data_root>/raw/<exchange>/<market>/_market/<stream>/<YYYY>/<MM>/<DD>/<HH>/...
```

例如：

```text
data/raw/okx/spot/BTC-USDT/trade/2026/08/04/12/...
data/raw/okx/spot/BTC-USDT/book_live/2026/08/04/12/...
data/raw/okx/spot/BTC-USDT/book_deep_snapshot/2026/08/04/12/...
data/raw/okx/perpetual/BTC-USDT-SWAP/ticker/2026/08/04/12/...
```

`instrument_key_encoded` 是完整 instrument key 的可逆 percent encoding；例如 Kraken `BTC/USDT` 会写成 `BTC%2FUSDT`。分区时间使用 collector 的 `received_at` UTC 小时，而不是可能缺失或异常的交易所 event time。

活动文件带 `.partial`。关闭时会完成 flush/sync，原子发布 `.jsonl.zst` 并写同名 `.manifest.json`。manifest 记录文件 SHA-256、record count、接收/事件时间、config SHA、egress、generation、gap/reconnect/校验/队列计数与持久化延迟。下游消费者只应读有效 closed manifest，不应读取 `.partial`。

每个 JSONL 行是 collector envelope 加交易所原生 payload，包含 exchange/market/instrument/stream、事件时间与接收时间、transport、connection generation、egress ID、完整性和 REST metadata。原始层不强行把五家 payload 改写成一个损失细节的通用 schema。

上述布局、writer、manifest 和恢复代码已实现；但由于长期交易所采集入口尚未完成，运行 `config check` 后看不到这些数据文件是正常的。

## 8. 30 秒及更大时间维度（尚未实现）

当前配置模型已支持：

```yaml
materializer:
  enabled: true
  delay: 5m
  intervals: [30s, 1m, 5m, 15m, 1h]
  revision_horizon: 24h
```

`intervals` 必须唯一、介于 30 秒和 1 小时之间，并且能整除一个 UTC 小时。配置顺序会自动规范为升序。`delay` 允许 0 到 60 分钟，用来等待已关闭 raw 小时分区。

计划中 materializer 将是独立批处理进程，只读 closed raw manifest，不读 `.partial`、不连交易所、不回压 collector，并输出：

| 数据集 | 计划中的主要内容 |
| --- | --- |
| `trade_bars` | OHLC、VWAP、base/quote volume、buy/sell/signed volume、trade count |
| `book_live_features` | mid、spread、microprice、depth、imbalance、stale、gap/有效性 |
| `book_deep_features` | 独立深度快照的 depth curve、bps/notional 流动性和窗口统计 |
| `derivative_windows` | mark/index/premium、funding、OI 及变化、risk/强平与 coverage |
| `quality_windows` | input count、latency、gap、reconnect、checksum、queue、限频和 interval stretch |

计划输出布局为：

```text
<data_root>/derived/<exchange>/<market>/<instrument_key_encoded>/<dataset>/
  interval=30s/date=<YYYY-MM-DD>/hour=<HH>/rev=0/*.parquet
  interval=30s/date=<YYYY-MM-DD>/hour=<HH>/rev=0/*.manifest.json
```

窗口将按 UTC Unix epoch 对齐并采用 `[start, end)`。live book 和 deep snapshot 依然独立物化，不会在汇总阶段暗中桥接。迟到 raw 数据会在 `revision_horizon` 内生成新的不可变 revision。

重要：目前 `src/crypto_collector/materializer` 和对应 CLI 不存在。将 `materializer.enabled` 设为 `true` 只能通过配置校验，不会自动创建 Parquet。

## 9. OSS、S3 和外部挂载 WebDAV（尚未实现）

参考片段位于 `config/examples/archive-targets.yaml`。将其 `archive` 子树合并到实际根配置或 profile 后，`config check` 可校验它：

```yaml
archive:
  targets:
    - id: oss-primary
      type: aliyun_oss
      required: true
      bucket: market-data
      endpoint: https://oss-ap-southeast-1.aliyuncs.com
      region: ap-southeast-1
      credentials:
        access_key_id: env:OSS_ACCESS_KEY_ID
        access_key_secret: env:OSS_ACCESS_KEY_SECRET
      compression:
        enabled: true
        mode: auto
        codec: zstd
        level: 3
        min_size: 1MiB

    - id: s3-secondary
      type: s3
      required: false
      bucket: market-data-backup
      region: ap-southeast-2
      credentials:
        access_key_id: env:S3_ACCESS_KEY_ID
        secret_access_key: env:S3_SECRET_ACCESS_KEY
      compression:
        enabled: true
        mode: auto
        codec: zstd
        level: 3
        min_size: 1MiB

    - id: webdav-mounted
      type: filesystem
      required: false
      root: /mnt/webdav/crypto-market-data
      mount_guard:
        path: /mnt/webdav/.collector-mount-id
        expected: env:WEBDAV_MOUNT_ID
      compression:
        enabled: false
        mode: off
```

WebDAV 策略是“由操作系统/rclone/davfs 等工具先挂载，项目再将它作为 `filesystem` target”，而不是内置 WebDAV HTTP 客户端。`mount_guard` 计划用来防止挂载掉线后误写到普通本地目录；仅检查目录存在是不够的。filesystem archive root 不能等于 `data_root`，也不能位于 `data_root` 内。

压缩可按 target 开启。计划中 `mode: auto` 只压缩达到 `min_size` 且尚未压缩的文件；已是 `.jsonl.zst` 或压缩 Parquet 的文件通常原样上传。`mode: zstd` 表示明确要求 zstd，而 `recompress: false` 是计划中防止重复压缩的默认值。

`required` 目标将是未来本地清理的强门槛。默认：

```yaml
local_cleanup:
  enabled: false
  grace: 24h
```

即只备份，不删除本地数据。未来即使开启清理，也应在所有 required receipt 强校验成功、materializer ACK（如启用）、grace/revision 保留期结束且没有活跃 lease 时才可删除。

重要：目前 archive 配置只会被解析和校验，不会上传、验证、恢复或删除文件。不应把 `config check` 成功当作备份已可用的证据。

## 10. 测试与在线 smoke

### 10.1 离线测试

默认 pytest 禁止外部 socket，可运行：

```bash
.venv/bin/python -m pytest -q
```

仅核对配置 CLI：

```bash
.venv/bin/python -m pytest tests/cli/test_config_check.py -q
```

检查代码质量：

```bash
.venv/bin/python -m ruff check src tests scripts
.venv/bin/python -m ruff format --check src tests scripts
PYTHONPATH=src .venv/bin/python -m mypy src
```

### 10.2 公开 API live smoke

只在明确允许联网时执行：

```bash
RUN_LIVE_API_TESTS=1 .venv/bin/python -m pytest --force-enable-socket tests/smoke -q
```

也可仅测一家交易所，例如 OKX：

```bash
RUN_LIVE_API_TESTS=1 .venv/bin/python -m pytest --force-enable-socket tests/smoke/test_okx_public_api.py -q
```

这些 smoke 测试会直接连接交易所公开 REST/WebSocket，不认证、不下单。它们只证明当前主机能够访问样本公开端点且基本响应结构符合预期，不证明长期采集、写盘、断线恢复、限频分流或备份已完成。它们也不使用 `config/network.yaml` 中的 SOCKS 出口。

live smoke 可能受地区限制、DNS/防火墙、当前交易所限频或 API 变更影响。不应在默认 CI 中强制运行。

## 11. 常见故障排查

### `collector: command not found`

项目尚未安装到当前 venv。重新执行：

```bash
.venv/bin/python -m pip install --no-build-isolation --no-deps .
```

也可以不依赖 console script，直接运行当前模块：

```bash
PYTHONPATH=src .venv/bin/python -m crypto_collector config check config.yaml
```

### `Invalid configuration: ...`

- 检查是否写了未知字段；模型禁止静默忽略拼写错误。
- 检查 duration/size 是否带明确单位。
- 如果存在 `config/network.yaml`，删除 `config.yaml` 中冲突的 `network:`。
- 整数盘口深度不得超过报告中的 `maximum_supported_depth`。
- `writer.flush_interval` 必须小于等于 `durability_slo / 2`。
- 磁盘比例必须满足 `critical < warning < recovery`。

### `missing environment variable` 或 `invalid secret configuration`

`config check` 会立即解析所有 secret 引用，包括尚未运行的 archive target。设置所需环境变量，或改用权限受限的绝对文件引用。SOCKS URL 的 scheme 必须与 `type` 一致。

```bash
chmod 600 /absolute/path/to/secret
```

secret 文件必须是普通文件、有效 UTF-8、不大于 64 KiB，且不能对 group/other 可写。loader 最多去掉一个末尾换行。

### 配置检查通过，但没有产生数据

这是当前预期行为。`config check` 明确不创建数据目录、不联网、不启动 worker。当前也没有面向用户的 `collector run` 命令。

### 多个出口仍然被限频

确认代理是否实际使用不同公网 IP。共享 NAT 的出口必须使用同一 `quota_group`，而且不应将调高 `max_http_concurrency` 误解为提高交易所限频额度。

### WebDAV 目录存在但不代表备份可用

当前尚无 archiver。未来接入后，还必须校验 mount guard 内容，确认该路径确实是外部挂载，不能只因目录存在就视为可用。

## 12. 安全与 secrets

- 不要在 YAML 中写代理密码、OSS key 或 S3 key 明文；只使用 `env:NAME` 或 `file:/absolute/path`。
- 文件 secret 建议使用 `0600` 权限，并放在仓库和 `data_root` 之外。
- `config check --json` 输出的是 secret 引用，不是解析后的值；secret 值轮换不会改变配置指纹。
- direct 出口不会偷用当前 shell 的 HTTP 环境代理。需要代理时必须显式配置 SOCKS egress。
- live smoke 会向外网发出匿名公开请求；在限制网络或 CI 中保持 `RUN_LIVE_API_TESTS` 未设置。
- 不要向本项目提供交易所交易/账户 API key。当前范围只需公开市场 API；archive 凭据仅用于备份目标。
- 将 `data_root` 和 `state_root` 放在受限目录，不要与公开 Web 根目录或多用户可写目录混用。

## 13. 下一个可验证里程碑

在把该项目当作实际数据采集器之前，至少要在 `collector --help` 中看到经测试的长期采集入口，并通过以下验收：真实交易所路由、断线/限频/书本 gap、有界队列、raw/manifest 关闭、SOCKS 分流、五家固定交易对，以及不包含 secret 的产物。materializer 和 archiver 应继续作为独立消费进程验收，不得反向阻塞采集。
